The problem

Retrieval is consulted too late

A vector-backed agent asks its knowledge base when the model decides the question is worth asking. On a small-looking ticket, it never asks. Retrieval didn’t fail. It was never invoked.

The button

“Change this button’s colour.” Looks like a one-line style change. The model looks up, finds nothing specific, and changes it.

→

The blast radius

That component is imported by a hundred subprojects across three teams. Nobody noticed until it shipped.

The needed knowledge wasn’t a document. It was a prior — this kind of thing, in this kind of directory, is shared. And nobody ever wrote it down. It accumulated, one reasonable decision at a time, over years.

The gate: a model never writes to gold. Static code verifies every proposed boundary against the rows it claims to cover, and a deterministic baseline has to be beaten — or the baseline wins and the notebook says so.

The trajectory is the product

We train on how work was done, not on what was shipped

Each window becomes a sandbox

  • CHAT.md — the discussion, in order
  • EVENTS.md — ticket status changes
  • COMMITS.md — files that landed
  • PULL_REQUESTS.md — review comments
  • REPO/ — the real files

Ten tools. The customer’s ten.

The agent replays the task with the exact tool schemas our harness ships, and every turn is recorded: message, tool, arguments, result, success.

list_dir · read_file · write_file · edit_file · search · run_command · make_dir · environment · diff · list_changes

1,167 calls validated

Loss is applied to assistant turns only. Tool results are masked — training on them teaches a model to invent its own tool output. That check caught 696 orphan results from one wrong key name before it could reach a GPU.

The moat

The model is fitted to the harness we already own

Every trajectory was generated by the same ten tools the customer runs. The model learned those schemas, their argument shapes, their failure modes and their recovery patterns — because it was trained on nothing else.
